# Root Authority Bootstrap R01 — Failure and Recovery

## General rule

Failure never promotes the target task. No automatic rebase, nearest-marker selection, partial
authority acceptance, standing retry or manual bypass is permitted.

```text
TARGET_READY requires both canonical refs and terminal bootstrap consumption.
Anything less remains BLOCKED_CANONICAL_AUTHORITY_REFERENCE_MISSING.
```

## Failure matrix

| Situation | Canonical effect | Recovery |
|---|---|---|
| Stage 1 merged; Stage 2 never started | Binding exists but no authority pair; target remains blocked | Owner may issue Grant 2 while Stage 1 blobs remain exact; otherwise revoke/expire |
| Stage 2 PR opened; head changes | No canonical authority effect | Revalidate exact head, diff and Grant 2 binding; unauthorized head is rejected |
| Stage 2 CI fails | No merge; no canonical records | Fix only within exact two-path scope or close/revoke; no manual authority promotion |
| SA local edit exists but EG generation fails | Working tree is incomplete; exact M/A validation fails | Delete only task-owned temporary files; regenerate both outputs from clean Stage 2 base |
| EG exists but SA resolver fails | Exact pair validation fails | Correct within exact paths only; no partial merge |
| Stage 2 merge succeeds but post-merge resolution cannot run | Git merge is canonical, but readiness is unverified | Report `MERGED / POST_MERGE_RESOLUTION_PENDING`; rerun read-only resolution; do not rerun merge |
| “Consumption record write” fails | Not applicable by design; consumption is derived from the same Stage 2 merge | If derivation cannot be verified, target remains blocked; no third write is attempted |
| Owner revokes active mode | No later merge allowed | Close the associated unmerged PR; retain history; new grant required for a new attempt |
| Main advances after Grant 1 | Stage 1 exact base mismatch | Grant 1 invalidated; owner must receive and ratify a fresh exact base |
| Main advances after Grant 2 | Stage 2 exact base mismatch | Grant 2 invalidated; rebase only after fresh owner-pinned Grant 2 |
| Stage 1 control-plane blobs change before Stage 2 | Reviewed protocol version changed | Stage 2 invalidated; new design/reconciliation or new Stage 1 binding required |
| Competing writer touches either Stage 2 path | Ambiguous authority materialization | Stop; competing writer must reach terminal disposition before a fresh Grant 2 |

## Atomic local materialization

Future implementation should render the SA row and EG file into task-owned temporary files
outside canonical paths, validate bytes and content, then replace both working-tree targets in a
bounded critical section. Before and after replacement it must verify:

1. Stage 2 base and branch are unchanged.
2. Decision Log source bytes still equal the expected base blob.
3. EG target is absent.
4. Both generated byte sequences are deterministic.
5. The complete Git diff is exactly `M decision-log.md` plus `A ...EG01.md`.

On any failure, only task-created temporary files may be removed. Existing governance files,
owner WIP and Git history are not reset, cleaned or rewritten.

## Merge atomicity

Git commits and squash merges publish one tree. Stage 2 therefore cannot canonically publish only
one member of the exact pair when changed-path validation is enforced. GitHub merge state, merge
SHA and fresh-main ancestry are verified before resolution.

## Rollback semantics

- Before merge: close the PR or revoke the grant; canonical main remains unchanged.
- After Stage 1 merge: do not revert merely because Stage 2 is delayed. The inert binding carries
  no authority pair and cannot activate the target.
- After Stage 2 merge: do not delete or rewrite authority history. A correction or revocation
  requires a separately authorized append-only governance action.
- A security defect discovered after Stage 2 merge blocks target execution until a separate
  owner-ratified repair; it does not authorize history rewrite.

## Manual closeout fallback

Manual squash fallback remains an emergency merge mechanism under the repository runbook. It
cannot replace Stage 1/2 validation, create missing authority or mark the target ready. Any manual
fallback must preserve exact head, scope, required checks, mergeability and owner authority and
must be reported as such.
